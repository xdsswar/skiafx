# Drag-resize invariants — do not break these

The drag-resize path is sensitive. Multiple changes during this project
each *individually* reintroduced the same family of "ScrollPane content
shrinks/expands/flickers/stutters" symptoms. The fix combinations took
multiple debugging passes to converge on. This file documents the
**invariants** the rendering pipeline relies on so they're not silently
re-broken in future work.

Every numbered invariant below is also in a code comment at the
relevant call site. Search for `RESIZE INVARIANT` in the tree to find
the exact spot.

## 0. Drag-resize stutter while effects are on — RESOLVED via NGNode gate (see #6)

Historically: with `SKIAPipeline.isEffectSupported() = true` and the
full effect engine live, each frame paid the GPU pipeline cost of
`saveLayer + SkImageFilter + restore` per effect-bearing node. Modena's
per-arrow scrollbar dropshadows + thumb shadow add up to ~3
effects/frame; during a continuous `WM_SIZE` the GPU pipeline barriers
took frame time from ~10 ms to ~100 ms → visible diffusion / smear of
the ScrollPane content during drag.

**Resolved by invariant #6 below:** the NGNode dispatch site now
queries `QuantumToolkit.isInLiveRepaint()` and treats `effectsSupported`
as `false` for the duration of the 100 ms drag-repaint window. That
short-circuits the FULL dispatch — `renderEffect → EffectFilter.render
→ PrEffectHelper.render` — including the source-content capture into a
fresh PrDrawable that the peer-level `shouldBypassForDrag()` couldn't
reach. Effects reappear the moment the drag stops.

A throttle on `liveRepaintRenderJob` (33 ms / 30 fps) was tested and
**rejected** — see invariant #7 for why. The right approach is to
paint per WM_SIZE event.

`SkPicture` caching of static effect outputs (Task #31) is still the
right long-term move — it would let effects render *during* drag with
cached output instead of being skipped — but the visible bug is gone.

## 1. `SKIAPipeline.isEffectSupported()` returns `false` until pooling exists

**File:** `modules/javafx.graphics/src/main/java/com/sun/prism/skia/SKIAPipeline.java`

Returning `true` makes `NGNode.renderEffect` dispatch every
effect-bearing node — including the Modena CSS `dropshadow` on every
scrollbar, menu, and tooltip — through the `SkiaEffectRenderer` per
frame.

Two distinct regressions can come from flipping this on prematurely:

1. **Passthrough churn** (Phase 2 regression): if the dispatched peer
   name falls back to `SkiaPassthroughPeer`, the framework around it
   still allocates a fresh `SkiaPrDrawable` per effect per frame and
   runs the intrinsic Merge composition. Avoidable by writing real
   peers for the hot-path dispatches.

2. **Per-frame `getCompatibleImage` allocation** (Phase 3 regression):
   even with real peers in place
   (`SkiaLinearConvolveShadowPeer`, `SkiaLinearConvolvePeer`,
   `SkiaBlendPeer`, etc.), each peer call goes
   `getCompatibleImage(w, h)` → `createCompatibleImage` →
   `factory.createRTTexture` → fresh GPU texture allocation. The JFX
   `ImagePool` in `Renderer.getCompatibleImage` is supposed to recycle
   these, but it pools by exact-size match and the slightly-different
   bounds generated by sigma rounding during a drag-resize keep
   missing the cache → churn → visible stutter under continuous
   `WM_SIZE`.

**Safe to flip back to `true`:** after `SkiaEffectRenderer.createCompatibleImage`
implements size-bucketed pooling (round w/h up to nearest power of 2
or to nearest 32-px tile, and hold a per-renderer recycle list of
recently-released drawables). Then the per-effect-per-frame cost
becomes a recycle lookup, not an allocation.

## 2. `SKIAPipeline.isUploading()` returns `false` for opaque windows

**File:** same.

Returning `true` makes `ViewScene.setStage` pick `UploadingPainter`,
which renders the scene into an offscreen RTTexture, reads the pixels
back to CPU, and uploads via Glass. On every drag-resize WM_SIZE the
offscreen RTTexture has to be destroyed and rebuilt at the new size
(allocation per frame), plus the per-frame GPU→CPU readback. Both
visible as the original "ScrollPane content shrinks and expands" /
"content overflows window" symptom.

**Always returns `false` for opaque stages**. Transparent / layered
windows are routed to `UploadingPainter` separately via
`WindowStage.needsUpdateWindow()` — that's the correct path for *those*
window types and isn't governed by this flag.

## 3. `openjfx_skia_surface_resize_gl` does not add any extra `SwapBuffers`

**File:** `modules/javafx.graphics/src/main/native-skia/shared/openjfx_skia_bridge.cpp`

The previous "nudge" — an extra `glClear + SwapBuffers` before
re-wrapping FBO 0 — was added to force Windows to reallocate the
default-framebuffer back buffer up front (Windows defers the buffer
shrink to the next SwapBuffers; without the nudge the *first* frame
after a shrink is drawn into the still-larger back buffer that DWM
then scales down → 1-frame compressed content).

But the nudge had two costs:

1. **DWM flicker.** At ~80 WM_SIZE events/sec during a fast drag, the
   nudge's slate-900 frame and the content frame alternate in DWM's
   composition queue → user sees flicker.
2. **Desktop ghost trails.** The extra ~3-4 ms in WndProc per resize
   tick keeps the FX thread inside `DispatchMessage(WM_SIZE)` long
   enough that DWM can't repaint the *desktop* area exposed by the
   moving window edge → ghost pixels from the previous window
   position linger outside the new window outline.

**Hard rule:** never re-add an internal `SwapBuffers`, `glClear`, or
aux-HGLRC clear to `surface_resize_gl`. The 1-frame soft-scale on
shrink is barely perceptible and disappears the moment the drag stops.
The ghost trail and flicker are noticeable; the soft-scale is not.

## 4. `PrRenderer.createRenderer` returns `null` when invariant #1 says effects are off

**File:** `modules/javafx.graphics/src/main/java/com/sun/scenario/effect/impl/prism/PrRenderer.java`

Even when `isEffectSupported()` is `false`, other code paths
(`Node.snapshot`, layered windows, programmatic effect chains outside
the scene-graph paint) still call `Renderer.getRenderer(fctx)` →
`PrRenderer.createRenderer`. Returning a real `SkiaEffectRenderer`
with mostly-passthrough peers under those paths *also* allocates fresh
drawables per call and reproduces the stutter symptom under any
animation that involves a snapshot.

**Hard rule:** these two flags move together. Either both off
(current state) or both on (after the real peer implementations land).

## 5. The minimal ScrollPane demo uses `AnchorPane` root + no `minWidth`/`wrapText`

**File:** `samples/ensemble/src/main/java/org/openjfx/samples/ensemble/EnsembleApp.java`

This is a demo-side invariant — not pipeline behaviour — but the
debug history makes it worth flagging:

- **`BorderPane` root** triggered ScrollPane skin's iterative `fitToWidth`
  solver in a way that interacted badly with the per-frame re-layout
  during drag-resize. `AnchorPane` resolves child positions from
  explicit anchors against its own bounds with no preferred-size
  negotiation — no feedback into the ScrollPane skin.
- **`VBox.setMinWidth(760)`** floored the content width and caused the
  fitToWidth solver to land in the cycle
  `viewport.width → nodeWidth → hbar visibility → viewport.width …`
- **`Label.setWrapText(true)`** gave content `HORIZONTAL` bias, so
  `prefHeight` depended on width, which fed the same cycle.

Any new ScrollPane demo should avoid these three together. They're
fine individually in isolation.

## 6. `effectsSupported` is dynamic; falls to `false` during live-repaint

**File:** `modules/javafx.graphics/src/main/java/com/sun/javafx/sg/prism/NGNode.java`

NGNode's effect-dispatch site reads
`pipeline.isEffectSupported() && !QuantumToolkit.isInLiveRepaint()`
each pulse instead of caching the pipeline answer at class init. When
the user is mid-drag (a `liveRepaintRenderJob` fired within the last
100 ms), the gate flips false and `renderEffect(g)` is skipped — the
node falls straight through to `renderContent(g)` with **no**
`EffectFilter.render` → **no** source-content capture into a
`PrDrawable` → **no** `saveLayer` / `SkImageFilter` / `restore` per
node per frame.

Without this gate, the per-frame GPU cost of the Modena scrollbar's
~3 effect-bearing nodes during a `WM_SIZE` storm shows up as visible
"diffusion" — the ScrollPane content appears to smear / oscillate
between sizes as the drag progresses because frame time goes from
~10 ms to ~100 ms and DWM stretches the lagging back buffer.

**Hard rule:** never re-convert `effectsSupported` back to a
`static final` boolean. The dynamic check is the whole point.
If `QuantumToolkit.isInLiveRepaint` is renamed or deleted, update the
NGNode call site to whatever the replacement drag-detection signal is
— do not drop the check.

The complement is `SkiaEffectRenderer.shouldBypassForDrag()`, which
guards the peer-level filter step for code paths that *do* dispatch
effects during drag (e.g. `Node.snapshot()` triggered programmatically
from drag handlers). Both layers stay; they catch different paths.

## 7. Do NOT throttle WM_SIZE-driven sync paints on the GL tier

**File:** `modules/javafx.graphics/src/main/java/com/sun/javafx/tk/quantum/PaintCollector.java`

`liveRepaintRenderJob` paints synchronously per WM_SIZE event. An
earlier attempt to throttle this to ~30 fps (32-33 ms minimum
interval) was tested and **regresses the bug**, not fixes it.

The throttle was supposed to let DWM rubber-band-stretch the previous
frame between paints. In practice what happens is:

1. Paint N goes into a back buffer that is at most 1 WM_SIZE behind
   the window (Windows defers FBO 0 reallocation to the next
   SwapBuffers — invariant #3). DWM stretches the buffer to the
   current window: stretch ratio ≈ 1 % at most.
2. During the 33 ms throttle gap, more WM_SIZEs fire and the window
   keeps shrinking/expanding. **The back buffer stays the same size
   the whole time**, so DWM's stretch ratio drifts continuously
   (content appears to compress smoothly).
3. The next paint happens. The buffer reallocates to the *new* size
   on the SwapBuffers. Content jumps back to "correct" size relative
   to the buffer, which DWM stretches with a near-1 ratio again.
4. Repeat at 30 Hz → **visible "shrink / expand in a loop"** — the
   exact diffusion symptom the throttle was meant to fix.

**Hard rule:** paint per WM_SIZE, no throttle. The unthrottled rate
(~80 Hz during a fast drag) keeps the back buffer at most ~12 ms
(~1-2 px of edge motion) behind the window — sub-pixel DWM stretch
which reads as softness, not oscillation. ~80 paints/sec is what
stock JFX has used on Windows for years; CPU is fine.

The `requestNextPulse()` settle hook **stays in place**: it arms a
post-drag pulse so the master timer (suppressed during the
DRAG_GATE_NANOS window) repaints once the drag ends, converging the
back-buffer size to the final window size cleanly.

If a future change introduces visible CPU pressure during drag, the
mitigation is a tiny throttle (≤ 8 ms) **only** as a CPU guard, never
as a "smoothness" mechanism. Skia's drag-resize smoothness comes
from painting frequently, not infrequently.

`-Dskia.resize.diag=true` prints one line per `liveRepaintRenderJob`
with timing + view size + action — used to confirm WM_SIZE delivery
rate and detect regressions.

## 8. `ImagePool.checkOut` sets content size back to the un-bucketed request

**File:** `modules/javafx.graphics/src/main/java/com/sun/scenario/effect/impl/ImagePool.java`

This is the long-running "ScrollPane content renders narrower than the
viewport" bug — visible as **content uniformly compressed by ~7-8%**
relative to its layout-reported width, leaving a too-wide gap between
content right edge and the scrollbar. Was present at every window
size, not just during drag-resize.

### The mechanism

`ImagePool.checkOut(renderer, w, h)` is JFX's pool for effect / clip
intermediate render-target textures. It does TWO stages of bucketing
before allocation:

1. `QUANT` round-up (16 px) — JFX-side, unconditional.
2. `renderer.getCompatibleWidth(w)` — for platform requirements.
   Our `SkiaEffectRenderer` rounds further to **128-px buckets** so
   drag-resize sigma jitter hits the same pool slot across frames
   (invariant #6 / Task #30 optimization).

A 947×640 request therefore becomes a **1024×640** physical drawable.

The pool was supposed to call back `setContentWidth(w_original)` /
`setContentHeight(h_original)` after allocation so the drawable's
LOGICAL content dimensions match what the caller asked for, while its
PHYSICAL backing texture stays at the bucketed size for re-use. But
those two lines were **commented out** with a comment dating from the
SW + J2D pipeline era:

```java
// The following calls to setContentWidth / setContentHeight
// should be uncommented only after the rest of the imagepool
// is fixed to handle a change in content size, and when both the
// SW pipeline and J2D pipeline are able to handle the change.
// eimg.setContentWidth(w);
// eimg.setContentHeight(h);
```

With them disabled the drawable claimed it was 1024 wide (the
bucketed physical size). `PrEffectHelper.render` reads
`image.getContentWidth()` to know what sub-rectangle to sample when
compositing the intermediate back to the main scene — it sampled the
entire 1024-wide physical texture and composited it to a 947-wide
target. **That's a horizontal squash by 947/1024 = 0.925.** Layout 906
rendered at ~838.

### The fix

The SW + J2D pipeline compatibility hold-over doesn't apply to this
Skia-only fork — neither pipeline exists. `SkiaTextureBase
.setContentWidth/Height` correctly updates the `contentWidth` field
that `Filterable.getContentWidth()` reads. So:

1. Stash the caller's request as `reqW, reqH` BEFORE bucketing.
2. After the cache-hit lookup, call
   `eimg.setContentWidth(reqW); eimg.setContentHeight(reqH);` — the
   previously-commented lines, re-enabled.
3. After a fresh `createCompatibleImage(w, h)` allocation, do the
   same to the newly-created drawable.

The drawable still has its PHYSICAL backing at the bucketed size
(1024) — so pool re-use across sigma-jittery frames still works as
designed — but its LOGICAL content width is now whatever the caller
asked for, so downstream samplers compose correctly.

### Why this also fixed drag-resize smear

During a fast drag, sigma jitter produces slightly-different requested
widths each frame (e.g. 940 → 935 → 928 → ...). All buckets to the
same 1024 physical drawable. Before the fix, each frame got
`contentWidth=1024` and composed it into a slightly-different target →
variable compression ratio every frame → visible "shrink/expand
oscillation". After the fix, the drawable's content dimensions match
the current frame's request, so composition is correct every frame.

**Hard rule:** do not re-comment those two `setContentWidth/Height`
lines. They are required for the bucketed pool to be visually correct.
The original "fix the rest of the imagepool first" prerequisite isn't
a thing in this Skia-only fork.

## Quick health check

After any change to the rendering pipeline, this minimum smoke:

```powershell
$env:SKIA_HOME = "F:/DEV/jskia/skia"
.\gradlew.bat :samples:ensemble:run
```

Expected steady state in the log:

```
Skia pipeline init order: skia
Skia pipeline initialised: com.sun.prism.skia.SKIAPipeline
INFO: Skia pipeline up: openjfx-skia-bridge/0.1 (skia-enabled)
[skia.painter] painter=PresentingPainter needsUpdateWindow=false isUploading=false
[skia] N.N fps  copies=0
[skia] N.N fps  copies=0
…
```

Then drag the window edges. Content must:

- Stay pinned to the viewport on shrink (no compress → snap-back loop).
- Not show ghost pixels lasting more than ~1 second outside the window
  on a fast left-edge drag (some lag is OS-side and unavoidable).
- Never flash slate-900 or any solid colour at the drag rate.

If any of those fail, walk back through invariants #1–#4 above. The
regression is almost certainly one of them.
